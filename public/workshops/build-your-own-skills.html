Part 1

What is
a skill?💡

A folder of instructions Claude reads when it's relevant. Nothing more.

Transition: "Let's start with the simplest possible definition." Take a beat.
Definition

A skill is a recipe card for Claude.

A folder you upload to Claude. It teaches Claude how to do one specific task — your team's report format, your brand voice, your weekly process — the way you want it done. Claude reads the recipe only when it's relevant.

The official definition: "A skill is a set of instructions — packaged as a simple folder — that teaches Claude how to handle specific tasks or workflows."

— Anthropic, The Complete Guide to Building Skills for Claude

04
Use the recipe analogy. A cookbook on the shelf doesn't slow down breakfast. But when you decide to make lasagna, the recipe is right there with the exact steps. Skills sit quietly until they're useful. Read the quote — having Anthropic's words behind you adds credibility.
Why this matters

Without a skill vs. with one.

Same task — checking the product idea board in YouTrack every Monday. Same data, same MCP. Different ask.

Without a skill

You, every Monday:

"Claude, use the YouTrack MCP to pull from our Product Ideas board (project PRD). Show me ideas in New status waiting to be reviewed, ideas rejected in the last 7 days, and ones accepted this week. Three numbers with one example each."

Re-typed every week.
Format drifts every time.

With a skill

You, every Monday:

"Claude, what's on the idea board this week?"

Claude reads the skill, queries YouTrack via MCP, returns the same three numbers in the same shape.
Same every Monday.

What the skill captures once: project ID, the three status buckets, the time window, the output format. Now anyone on the team can ask "idea board?" and get the same answer.
05
Lead with the payoff. Read the "without" out loud — every Monday, retyping the same setup. Then the "with" — three words. The contrast does the work. Real internal context: the YouTrack Product Ideas board (project PRD). The skill encapsulates the project ID, the status buckets (New / Rejected / Accepted), the 7-day window, and the output shape. Anyone on the team can ask the question without knowing the YouTrack internals. This is also a teaser for the patterns later: this skill combines MCP (YouTrack) with a workflow skill (the format and time window).
What people build

Two kinds of skills.

Almost every skill is one of these. Pick whichever matches what you actually do at work.

Type 1 — Task consistency

Same task. Same shape every time.

No external data needed. The skill teaches Claude your format, tone, conventions, brand voice — so the output is the same whether you ask on Monday or Friday, and whoever asks.

Examples: /brand-assets, /reprompt

Type 2 — Workflow with MCP

Connect → process → output.

The skill calls an MCP to pull live data (Salesforce, YouTrack, Notion), applies your team's process, and returns it in your shape. MCP at the start, the end, or both.

Examples: /salesforce-forecast, /salesforce-churn-check, the YouTrack idea-board skill

The kitchen analogy (from Anthropic's guide): MCP is the professional kitchen — tools, ingredients, equipment. The skill is the recipe — step-by-step instructions. MCP is what Claude can do. The skill is how Claude should do it. Type 2 bundles the two so a teammate just orders dinner.
06
The binary: every skill is either consistency-only (Type 1, no external data) or workflow-with-MCP (Type 2, pulls or pushes data). Don't pretend there's more nuance — those are the two patterns. Map the skills explicitly: brand-assets and reprompt are Type 1 (no MCP). Salesforce skills and the YouTrack idea-board are Type 2. The kitchen analogy is straight from Anthropic's guide — MCP = kitchen, skill = recipe; MCP is "can do", skill is "should do". This frame is the simplest way for the audience to decide what they should build next.
Part 2

Inside
a skill.🔍

It's just a folder with one important file. Let's open it up.

Transition: "Now we're going to look at the actual structure." Reassure: this is the only part that looks technical, and it's just a text file.
Folder structure

A skill is a folder.

The folder name becomes the skill name. Inside, only one file is required: SKILL.md. Everything else is optional helpers — most skills don't need them.

weekly-status-update/ # Folder name in kebab-case
├── SKILL.md required # Your instructions (the only file you need)
├── scripts/ optional # Code Claude can run
├── references/ optional # Long docs loaded only when needed
└── assets/ optional # Templates, logos, fonts
Naming rules that actually matter: folder name in kebab-case (lowercase, hyphens — no spaces, no capitals). The file inside must be spelled exactly SKILL.md — capitalised, with a dot.
If you add scripts or references: tell SKILL.md how to use them. "Before drafting, consult references/style-guide.md" or "Run scripts/validate.py to check the data". Without that pointer, the files just sit there — Claude won't reach for them on its own.
08
Reassure: only SKILL.md is required. Today they will not touch scripts, references, or assets. Highlight the naming rules — these are the #1 cause of "my skill won't upload" errors. Then the second callout: optional files are inert unless SKILL.md references them. Show one example aloud: "Before drafting an email, consult references/tone.md" — that's the pattern. Without that pointer, the file is dead weight.
The one file you write

SKILL.md has two parts.

Part 1 — The label (frontmatter)

Between two --- markers. Tells Claude the skill's name and when to use it. This is the only part Claude always sees.

Part 2 — The instructions (a really good prompt)

Everything below the label. This is a prompt — the same kind you'd write in chat, just polished. Clear task, specific format, examples, constraints. Claude reads it only when the label says it's relevant.

---
name: weekly-status-update
description: Writes my weekly status update. Use when I ask for a
  "weekly update", "status report", or "Friday recap". Output is
  ~200 words in three sections (wins, blockers, next week).
---

# Weekly Status Update

Write the update in three sections...
The shortcut: a skill's body is essentially a really good prompt. Use our /reprompt skill to turn rough notes into a polished one — then paste the result in as your instructions. You already know how to write skills; you just didn't know it.
09
Walk through it slowly. The three dashes (---) are just markers separating the two parts. The "name" matches the folder. The "description" is the most important line — we spend the next slide on it. Below the dashes is just markdown — same kind you'd write in Notion. Then land the big insight from the callout: the body of a skill IS a prompt. Reference the reprompt skill from Workshop #2 — if they got good at writing prompts there, they already know how to write skills. The /reprompt skill is the easiest way to bridge: take rough notes, run them through /reprompt, paste the polished output into SKILL.md.
How Claude reads it

Claude reads it in three layers.

Each layer only loads if the layer above said it was relevant — which is why you can have many skills installed without slowing anything down.

01

The label (frontmatter)

The skill's name and a one-line description of when to use it.

Always loaded
02

The instructions (SKILL.md body)

The full how-to. Format, steps, examples, tone.

Loaded when relevant
03

Extras (linked files)

Scripts Claude can run, long references, sample outputs, templates.

Only if needed
10
Right after seeing the SKILL.md's two parts. Land the loading mechanism: Layer 1 (the label) is always in context — that's how Claude decides whether to use the skill. Layer 2 (the body) only loads if Layer 1 said "yes". Layer 3 (extras like scripts and references) only loads if Layer 2 needs them. This is the setup for the next slide — the description is the magic, and now they know why.
★ The most important line

That's why the description is the magic.

Layer 1 is the only line Claude always has loaded. Get it right and your skill triggers reliably. Get it wrong and Claude never picks it up — even if the rest of the skill is perfect.

Too vague — won't trigger

"Helps with reports."

No trigger words. No specifics. Claude won't know when to use it.

Specific — triggers reliably

"Writes my weekly status update in three sections. Use when I say 'weekly update', 'status report', or 'Friday recap'."

What + when + actual words I'd say.

The formula: [What it does] + [When to use it] + [Trigger phrases the user actually says].
11
Single most important slide of the deck. Now that they know Layer 1 is always loaded, it's obvious why the description matters. Tell them: write down the actual words you'd say — "weekly update", "Friday recap", whatever you actually type. Include 3-5 variations. If they remember nothing else, remember the formula.
The optional folders

Scripts, references, and assets.

When SKILL.md alone isn't enough. Add these only when you need them — but knowing what each unlocks helps you spot the right moment.

scripts/

Code Claude can run

Python or bash scripts the skill executes. Use when the task needs real determinism — validation, data processing, generating files from templates.

"Code is deterministic; language interpretation isn't." — Anthropic's skills guide

references/

Long docs, loaded on demand

API references, style guides, full domain knowledge. Keep SKILL.md focused on the core flow — point to references/ for material that only loads when Claude reaches for it.

Example: references/api-patterns.md for rate limits, pagination, error codes.

assets/

Files used in output

Templates, logos, fonts, icons. Used in what Claude produces — not in what Claude reads. Add them when output needs brand polish.

Real example: /brand-assets Bundles the company logos and colors here.

12
Drill into the three optional folders from the very first slide. Most first skills use none of these. But each unlocks a real capability. Scripts = determinism (Office skills are the canonical example — code beats prompting for validation). References = long material that only loads when relevant (Layer 3 of progressive disclosure they just saw). Assets = brand consistency in output (our /brand-assets skill is a real example). Tie it back: all three only get used when SKILL.md explicitly tells Claude to reach for them.

Scopes

Same file. Four places it can live.

Skills work everywhere Claude does — but you choose who can see them. Pick the scope that matches who needs the skill.

Bundled

Built into Claude

Skills Anthropic ships with Claude itself — /skill-creator, /code-review, /debug, others. You don't manage these.

Everyone
Personal

Just for you

You upload it to your account. Active in every chat and every Cowork session — but only yours. Where most people start.

Only you
Shared

From you, to colleagues

Your personal skill, shared via Customize → Skills → Share. Send to specific people by name/email, or publish to your org's directory. Team/Enterprise plans only.

Colleagues you pick
Org-provisioned

The whole workspace

The Team or Enterprise owner provisions a skill from Organization settings → Skills. Appears for every member, view-only.

Everyone in your org
14
Mental model: same skill file, different reach. Most people start with Personal — that's what we'll build in the walkthrough. Team vs Org matters: Team is your immediate Team-plan workspace, provisioned by the owner. Org is enterprise tier, deployed via managed settings with policy controls. They're different product tiers. The footnote about Claude Code repos is for devs in the room — true repo-level "project skills" only exist in Claude Code today, not in chat/Cowork. Don't promise per-Project scoping for Claude.ai; the docs don't currently support it.
Get a personal skill

Build it. Or import it.

Two paths to your first personal skill. Pick whichever matches where you're starting from.

Path A — Build it inside Claude

You don't have a folder yet — start from a conversation.

  • /skill-creator — Anthropic's built-in skill. Walks you through name, description, and instructions. Outputs a ready-to-use SKILL.md.
  • /reprompt — describe what you want as a task. The polished prompt it returns is your SKILL.md body — wrap it with frontmatter, done.

Fastest path for first-timers. No file handling.

Path B — Get one someone else built

Three sources, one install flow.

  • Marketplace: browse github.com/anthropics/skills and grab the folder.
  • A colleague: they DM you a .zip or share it via Claude.
  • The internet: point Claude at a URL or paste a SKILL.md you found — ask it to package the folder for you.

Install: Customize → Skills → Upload .zip → Toggle on.

Cowork bonus: the + in the Customize sidebar opens your org's directory — skills colleagues have already shared with the team. Check there before building from scratch.
15
Two starting points. Path A: build from a conversation — /skill-creator is Anthropic's official walkthrough, /reprompt is the in-house option from Workshop #2. Path B: get a skill someone else built — from the marketplace at github.com/anthropics/skills, from a colleague, or from any URL on the internet (Claude can read it and package the folder). The Cowork bonus is the underrated piece: if someone on your team already built it, you don't have to.
Two paths to your team

You share. Or your owner provisions.

Both end up in front of colleagues — different mechanism, different control.

Path A — You share (user-initiated)

From inside Customize → Skills → Share:

  • Specific people: enter names or emails — they get a notification.
  • Entire org: publish to your organization's skills directory.

Recipients can enable and use the skill, but can't edit it.

Path B — Owner provisions (admin-initiated)

From Organization settings → Skills:

  • Owners of Team or Enterprise orgs can provision skills for all users.
  • Pushes to every member automatically — view-only.

Best for shared standards your whole team should follow.

One gotcha: sharing is off by default. The owner has to flip Share with organization and/or Skill sharing toggles in Organization settings before the Share button appears for anyone.
16
Two distribution paths. Path A is the new important one most decks miss: any user can share a skill they built — to named colleagues or the org's directory. No admin needed (assuming sharing is enabled). Path B is the heavyweight version: owner pushes a skill for everyone, view-only. The "off by default" gotcha is real — flag it to any owners in the room. They might not realize they need to flip a switch.

under the hood.🔬

/salesforce-churn-check — architecture, snippets, output, and why each folder earns its place.

Pivot from concept to a real example. Frame this as a tour, not a live build — we're walking through the salesforce-churn-check skill that's about to ship. Four slides: the value (why it exists), the architecture (file tree), inside the SKILL.md, the output. Then one closer slide on why references and scripts matter. By the end, the audience should be able to spot the same patterns in any other Type-2 skill.
Case study · /salesforce-churn-check

Why this skill exists.

Surface B2B accounts whose Flash Test cadence has collapsed vs their own historical baseline — a churn signal the existing Salesforce dashboards can't catch.

What Salesforce already shows
  • Total tests per day / week / month
  • Last-activity date per account
  • Terminations (after they happen)

A daily-tester quiet for 7 days = alarming. A monthly-tester quiet for 7 days = normal. Salesforce can't tell the two apart.

What the skill adds
  • Anyone can query Salesforce. No SOQL, no field-name gotchas, no docs to skim.
  • Plain-English chat. "Who's gone quiet?" — the skill orchestrates the rest.
  • Complex workflow, hidden. Per-account baselines, country holidays, YoY check — all behind one prompt.
  • Composes with skills + MCPs. Brand it via /brand-assets, ping owners on Slack, email it to a customer — chain any connector your team has.

The CSM gets to act, not query. Salesforce expertise stops being a bottleneck.

18
Lead with value, not features. The skill's real contribution isn't the SOQL it generates — it's that nobody on the team needs to know SOQL anymore. Plain-English chat now answers Salesforce questions. Complex workflow (per-account math, holidays, YoY) is hidden — the CSM just gets the answer. And the underrated win is composability: the output can flow anywhere. Chain with /brand-assets to brand the report, Slack MCP to ping the account owners, Gmail MCP to email a customer follow-up, /salesforce-forecast for trend context. The skill is one node in a larger workflow you compose. That's the Type-2 sweet spot from Part 1.
Architecture

Three layers, working together.

All three optional folders show up in a real Type-2 skill — each plays a distinct role.

salesforce-churn-check/
├── SKILL.md required # The 7-step flow Claude follows
├── references/
│ └── filter-rules.md reference # Canonical SOQL filter — loaded only when querying
└── scripts/
├── find_quiet_accounts.py script # Deterministic math: workdays, ratios, severity
└── requirements.txt script # Python deps (the holidays package)
What's where, and why: SKILL.md orchestrates. references/ holds rules too dense to inline (gotchas like Not_Billable__c = false meaning is billable). scripts/ does the math — code is deterministic; language interpretation isn't.
19
Walk through the file tree. This is the canonical pattern for a Type-2 skill: SKILL.md as orchestrator, references/ for dense canonical rules (the Salesforce filter has 8 conditions and 4 gotchas — moving it out keeps SKILL.md readable), scripts/ for math (holiday math + ratio math + severity bands — Python beats prompting for any of these). README.md is for humans browsing the repo, NOT loaded by Claude. Most first skills don't use any of these folders. The churn-check skill uses all three because it earned each one.
Inside SKILL.md

The label, then the recipe.

The frontmatter carries the trigger phrases. The body points Claude to references/ and scripts/ exactly when needed.

---
name: salesforce-churn-check
description: "Find B2B accounts whose paid Flash Test cadence has
  collapsed vs their OWN historical baseline... Triggers on:
  'who has gone quiet', 'which accounts stopped testing',
  'churn signals', 'silent customers', 'accounts at risk',
  'drop in testing', 'inactive accounts', 'churn check',
  'where should CSM look'."
compatibility: "Requires Python 3 with the holidays package
  and the Salesforce MCP."
---

# Salesforce pulse check

## Critical: read references first
Before constructing any SOQL, read `references/filter-rules.md`
for the canonical Filter A and the Rule-0 aggregate cap.

### Step 1 — Baseline counts per account: days 30–90 ago (60-day window)
### Step 2 — Recent counts per account: last 30 days  ← the comparison vs Step 1
### Step 3 — Same baseline window, 52 weeks back  (year-over-year check)
### Step 4 — Same recent window,  52 weeks back  (year-over-year check)
### Step 5 — Join Steps 1–4 by AccountId, write /tmp/churn.csv
### Step 6 — Run scripts/find_quiet_accounts.py — workdays, ratios, severity
### Step 7 — Present the ranked watchlist with owners to ping
20
Read the description aloud — nine trigger phrases, all real things a CSM would type. Then the body: notice the explicit "read references first" pointer (Part 2's optional-files rule in action). The 7 steps form a 2×2 matrix via the Salesforce MCP — Step 1 baseline (30–90 days ago), Step 2 recent (last 30 days, the comparison point), Steps 3+4 are the same two windows shifted 52 weeks back for the YoY seasonality check. Step 5 joins them into a CSV. Step 6 runs Python for workday math, ratios, severity bands, seasonal flag. Step 7 composes the answer. The CSM types five words; the skill orchestrates seven steps invisibly.

A ranked watchlist, owners attached.

Closing the case study

Why references and scripts earn their place.

Neither folder is decorative. Each one absorbs work that would otherwise be in SKILL.md — making the skill faster, cheaper, and more reliable.

references/ — Claude's dictionary for your setup

Tells Claude what your domain words mean.

  • Which Salesforce fields define a "paid Flash Test"
  • What "active license" maps to in the schema
  • The 8-clause filter with all its gotchas (e.g. Not_Billable__c = false means is billable)
  • Aggregate caps, naming conventions, rules of the data

Without it: Claude guesses field names. With it: Claude follows the canonical rules.

scripts/ — Deterministic work Claude shouldn't do

Code beats prompting for boring math.

  • Severity thresholds (10% critical / 40% concerning / 70% watch)
  • CSV joins across 4 query results
  • National holiday calendars per country (Python's holidays package)
  • Workday math, ratio math, seasonal-flag logic

Faster, cheaper, exact. Claude is overkill for math — and an LLM can't import Python's holiday package.

The principle: use Claude for judgement, scripts for math, references for vocabulary. Each one earns its place — and your SKILL.md stays focused on the flow.
22
This slide answers "why bother with the optional folders?" References are vocabulary — they teach Claude your domain's words. Without filter-rules.md, Claude would guess field names and get them wrong (Not_Billable__c = false is the canonical example — sounds like "not billable" but means IS billable). Scripts are math — deterministic operations that don't need an LLM. Severity thresholds, holidays, workdays, CSV joins. All things Claude COULD do but shouldn't, because code is faster, cheaper, and exact. The principle line is the take-home: judgement / math / vocabulary. That's how to think about what goes where.
Part 5

The workflow,
start to ship.⚙️

Build → smoke test → peer review → iterate → distribute.

Energy shift. Most workshop attendees will leave able to write the SKILL.md, but the gap between "I wrote one" and "it works in production" is the workflow. Walk them through the loop. Emphasize: no step is optional — most failed skills skipped review or shipped without iterating.
The lifecycle

Five phases. None optional.

Every skill that lands in production runs this loop. Skip a phase and you'll find out the hard way — by shipping something that triggers wrong or embarrasses you in a team chat.

1

Build

Write SKILL.md. Description + instructions in plain English.

2

Smoke test

Trigger it yourself 3–5 times. Check output. Check speed.

3

Peer review

Have another LLM (or reviewer prompt) critique what you built.

4

Iterate

Fix what came back. Re-test. Repeat until it feels solid.

5

Distribute

Share via Claude, zip the folder, or push as an org skill.

24
Set the frame: build is the easy part — everything after it is what makes the difference. Most skills that don't work in practice failed at phase 2 (the author never actually tested it) or phase 3 (no one else looked at it before it shipped). The five-phase frame is what the next slides expand on, one at a time.
Phase 2 · smoke test

Run it yourself. Check four things.

Trigger your skill 3–5 times with realistic inputs. For each run, look at these four dimensions before showing it to anyone else.

1 / Triggering

Does Claude actually pick the skill up when you ask? If not, the description's trigger phrases need work.

2 / Speed

How long does it take? Acceptable for the workflow? Can you trim the body to run faster without compromising output quality?

3 / Output format

Is it readable? Trim useless info that's bloating the response. Headers, bullets, length — all easy to tighten.

4 / Output quality

Is the data granular enough? Precise where it needs to be? Or vague, hallucinated, missing the specifics that matter?

If anything feels off — straight back to Phase 1 (build) and fix it. No skill ships from smoke test directly.

25
These four checks are non-negotiable. Triggering catches "wrong description" bugs. Speed catches bloated SKILL.md files. Format catches sloppy instructions. Quality catches vague or hallucinated requirements. Run the skill in chat 3-5 times — vary the input slightly — and judge each dimension before showing it to anyone. Speed is the one people skip; flag it. Slow skills don't get used, no matter how good the output.
Phase 3 · peer review

Have a second agent check it.

The same model with the same blind spots can't catch its own errors. Two patterns to outsource the review — pick one, or run both for higher catch rate.

Pattern A — Critique prompt

Reviewer agent grades the same four checks.

  • Different LLM: paste SKILL.md + a sample output into ChatGPT or Gemini — fresh blind spots.
  • Reviewer role: fresh Claude chat, "you are a senior reviewer", ask it to grade triggering / speed / format / quality.
  • Or both: highest catch rate for anything you'll ship team-wide.
Pattern B — Comparison prompt

If you have ground truth, diff against it.

  • Paste your skill's actual output + the expected output into a fresh Claude chat.
  • Ask: "where do these differ, and which differences matter?"
  • Claude surfaces specific gaps — missing sections, wrong tone, hallucinations.

Only works when you have a known-good example to compare against.

Same chain as Workshop #2: producer → reviewer → refiner. Don't bake the reviewer into the same prompt — same model, same blind spots.
26
Two patterns. Pattern A (critique prompt) is the universal move — works for any skill, no setup. Pattern B (comparison prompt) is more powerful but needs ground truth, so use it for high-stakes skills where you can write what "right" looks like. For team-wide skills, run both. Reference Workshop #2's producer/reviewer/refiner chain so the pattern feels familiar — they already know this from prompts; same idea, applied to skills.
Phase 4 · iterate

Fix what came back.

Each of the four checks maps to a kind of fix. Expect 2–3 cycles before a skill feels solid. Most fixes live in the description or instructions — not in code.

Triggering issues

Under: add more trigger phrases — words you'd actually say.
Over: narrow the description, add "Do NOT use for…" to scope it.

Format issues

Output too verbose, hard to scan, or wrong shape. Trim the instructions — fewer rules, more examples of the right output.

Quality issues

Output vague, hallucinated, or low granularity. Tighten requirements in the body. Add a sample of "good" so Claude has a target.

Speed issues

Skill takes too long. Cut anything not strictly needed. Move long reference material to references/ so it loads only when needed.

The debug trick still works: ask Claude "When would you use the [skill-name] skill?" It quotes the description back. If the answer is too broad or too narrow — you've found your fix.
27
Four feedback categories map cleanly to the four smoke-test checks. Most fixes are description edits (triggering) or body trim (speed). Format and quality fixes usually live in the body too — sharper rules, better samples. The debug trick is the cheapest way to validate description changes. Mention: 2-3 cycles is normal — anyone who claims their first version was perfect is lying or has very low standards.
Phase 5 · distribute

Three ways to ship it.

Once your skill passes review, pick the distribution that matches the audience.

01 / Share from Claude

Share via the UI

Open your skill in Customize → Skills → Share. Send to specific people by name/email, or publish to your org's directory.

Use when: Team/Enterprise plan with sharing enabled.

02 / Zip & send

Send the file

Compress the folder. Drop the .zip in Slack, email, or DM. They upload via Customize → Skills.

Use when: no Team plan, or sharing isn't enabled yet.

03 / Owner provision

Owner pushes it

Hand the .zip to your Team or Enterprise owner. They provision it from Organization settings → Skills — everyone gets it, view-only.

Use when: it's a shared standard for the team.

28
Map the distribution to the audience size: one person → share link; team → zip; whole org → admin provisions. Most internal skills will go through routes 2 or 3 because they reference internal context (internal-specific). Route 1 is for skills that have public value. Highlight: if it's worth your team having it, push it to the admin instead of asking each person to upload separately.

Build your own

Four questions to start.

Pick a task you repeat. Walk these in order — your SKILL.md falls out the other end.

1

What do I keep retyping?

The prompt you've sent more than twice is your skill candidate. Vague isn't enough — you need a task you do regularly.

2

Type 1 or Type 2?

Does it need live data from an MCP (Salesforce, YouTrack, Notion), or is it just task consistency (brand voice, weekly format)? That's the shape.

3

What words trigger it?

The actual phrases you'd say — "weekly update", "idea board", "draft an email". Three to five variations. That's the description.

4

What's the output shape?

Length, sections, tone, hard rules. Write a sample of what "good" looks like — that goes in the body.

Don't have a folder yet? Use /skill-creator or /reprompt to turn these four answers into a SKILL.md.
31
The thinking model. Four questions, in order, that produce the inputs you need to write a SKILL.md. Walk through aloud — pick a real task from the room if there's time. Question 1 is the filter (vague ideas don't survive). Question 2 is the Type 1/Type 2 binary from Part 1. Question 3 is the description (we hammered this earlier). Question 4 is the body. Land the callout: if writing it from scratch feels hard, /skill-creator or /reprompt does the assembly — they just answer the four questions in chat.
The take-home

If you remember nothing else.

1

A skill is a folder with one file. SKILL.md is plain English instructions Claude reads when they're relevant — nothing more.

2

The description is the magic. Write it using the actual trigger phrases you'd say. That single line decides whether your skill ever runs.

3

A skill's body is a polished prompt. Use /reprompt from Workshop #2 to turn rough notes into one — then drop it in.

32
This is the take-home callout in the style of Workshops #1 and #2. Each previous workshop closed with three "if you remember nothing else" lines. Reading them aloud should feel like a recap, not new material. Land hard on number 2 — that's the only thing in the whole skill file that has to be excellent. The others can be rough; the description has to be sharp.
